# Local access and file backup design — 0.3.0

## User flow

1. First launch: choose a name and a password of 8–256 characters. Existing device activities are retained. The name personalizes Today.
2. Cold launch: enter the local password. Lock app is available in Settings → Profile & Backups.
3. Choose a backup folder in Files, outside AnchorOS. A write probe checks access before saving its bookmark. An empty folder enables automatic copies and verifies the first copy. Existing backups require review/confirmation before device activities become the next copy.
4. Changes persist on device first. When enabled, immutable encrypted copies run after a 15-second quiet period, within 60 seconds of continuous edits, on app activation/reconnection, and best effort when backgrounding. iOS does not promise scheduled work while closed.
5. After reinstalling: choose a saved `.anchorbackup` file on the welcome screen, enter its original password, review counts/name, and confirm. The profile and activities are restored; running timers become paused. Select the folder again to resume copies. An app cannot retain its folder permission bookmark across deletion of its container.

## Data and password boundaries

The local password is an app lock, not an online account. Its verification record contains an AES-GCM-encrypted fixed proof, public name/profile ID, random salt/nonce, and authenticated algorithm metadata. The password and derived key are never persisted. Keys are cleared from JavaScript memory on lock; platforms may retain temporary managed-memory copies until reclamation.

Backup contents are encrypted with AES-256-GCM. PBKDF2-HMAC-SHA256 uses a 16-byte random salt and 600,000 iterations. Every encryption uses a fresh 12-byte random nonce and 128-bit authentication tag. The complete header is canonical JSON authenticated as additional data. Header/profile/revision/hash changes therefore invalidate decryption. Algorithms and iteration bounds are validated before password work. Backups are capped at 16 MB; decrypted domain/vault input remains capped at 8 MB.

Browser cryptography uses WebCrypto. The iPhone bridge uses the same format through CommonCrypto and CryptoKit. CI compiles the shared native helper on macOS and tests ASCII/Unicode password vectors generated by WebCrypto, byte-for-byte ciphertext, SHA-256, round trips, and tampered headers. It then compiles the iOS host.

Internal activity files continue to use atomic iOS file protection or IndexedDB transactions/origin controls. This change does not encrypt those activity files with the app password. Encrypted external/portable copies are the recovery mechanism after the container is deleted. There is no password recovery service; losing the original password prevents opening its encrypted copies.

## Files and retention

The native directory picker grants scoped access. Minimal bookmarks are resolved at use, stale bookmarks refreshed, and access released after each operation. NSFileCoordinator manages provider reads/writes/deletes. The app rejects its own container as a destination, checks selection tokens on native operations, restricts filenames to generated `anchoros-<time>-<uuid>.anchorbackup` names, writes atomically without replacing existing copies, and reads/decrypts/hash-checks a copy before acknowledging it locally.

Only after a durable acknowledgment may retention remove a previously decryptable copy. Keep 20 recent revisions plus daily copies for 30 days. Unsupported/damaged files are never pruned. Missing permissions, unavailable providers, storage failures, and mismatches stay visible and do not acknowledge an unfinished copy. Retry/backoff and interrupted-write deduplication remain in the controller.

A local folder outside AnchorOS can survive deleting AnchorOS. Files can still be lost if the user deletes them, removes the provider app, or loses the device. A provider may store them locally or synchronize them separately; AnchorOS does not require or configure a cloud account. Browser sessions support encrypted export/import, but automatic directory access is implemented in the iPhone host.

## Migration and limits

AppState remains version 2 and device vault format 1. Existing active activities/rollback are copied into the new local profile; older datasets remain in the protected vault rather than being silently erased. Older plain portable snapshots remain importable after local unlock and explicit review. Remote sign-in code, SDK, callback setup, OAuth inputs, and API calls have been removed.

Required physical-device checks are in SETUP.md. Web tests and a successful Xcode build cannot certify a particular Files provider's permission persistence, revoked access, or app deletion behavior.
